# Tatoeba N5 candidate evaluation

Downloaded on 2026-10-06 from the official Tatoeba exports. `coverage.json` records source URLs, byte counts, SHA-256 checksums, vocabulary checksum, coverage, and unmatched words. Raw inputs are retained locally in `data/tatoeba/raw-snapshots/2026-10-06/`, with all three SHA-256 checksums verified against `coverage.json` and recorded in `manifest.json`. The corpus files are Git-ignored; back up or transfer this directory separately with release data. These weekly URLs change, so downloading them again does not reproduce this snapshot.

## Result

147,836 indexed pairs scanned. Of 718 distinct N5 headword/reading pairs, 557 have candidates (77.6%); 863 candidate records retained, up to three per word. Zero examples are approved. Matching is exact headword plus index reading where supplied; ambiguous readings are rejected. Only checked-usage (`~`) entries are selected, with Japanese length at most 80 characters and English at most 200. Text must agree with the detailed sentence exports. These filters do not prove the intended meaning, naturalness, translation accuracy, or suitability for N5 learners.

The CSV's meanings are not JMdict sense IDs. For example, the candidate for ああ uses the “that way” sense, while our CSV gloss is “Ah!, Oh!”. Reviewers must verify meanings as well as grammar and translations. Missing matches remain missing; do not manufacture examples or use substring matching as a substitute. Sentence readings are null until separately verified.

## Reproduce

Download the three URLs listed in `coverage.json` into a raw directory, then run from the repository root:

```sh
python3 tools/data/prepare_tatoeba.py --raw data/tatoeba/raw-snapshots/2026-10-06
python3 tools/data/build_approved_examples.py
python3 tools/data/export_review_sheet.py
python3 -m unittest discover -s tools/data -p 'test_*.py' -v
```

The standard-library script is deterministic for the same inputs. Outputs live outside `Frameworks/DataKit/Resources`, so they are not shipped in the app. Candidate review status is always `pending`. The production builder reads `approvals.json` and emits only human-approved examples to `approved-examples.json`, plus `approved-coverage.json`. Current output is **0 approved words of 718**; the empty bundle is preparation output, not a published example feature. No app resource is generated by this command.

## Human review ledger

`approvals.json` has `formatVersion: 1` and a `reviews` array. Keep it empty until a fluent human reviewer has assessed the intended CSV meaning, Japanese naturalness, English translation and learner suitability. Record rejections as well as approvals; automatic index matching does not satisfy this gate. Test fixtures in the Python suite are synthetic and are never production decisions.

Each decision identifies one exact candidate:

```json
{
  "word": {"headword": "exact CSV headword", "reading": "exact CSV reading", "level": "N5"},
  "japaneseId": "source numeric ID",
  "englishId": "source numeric ID",
  "japaneseSha256": "SHA-256 of the Japanese UTF-8 text, without a newline",
  "englishSha256": "SHA-256 of the English UTF-8 text, without a newline",
  "status": "pending | rejected | approved",
  "reviewer": "human reviewer name or stable credit",
  "reviewedOn": "YYYY-MM-DD",
  "verifiedSense": "Explain how the example matches the CSV gloss, or why it was rejected",
  "reviewedReading": null
}
```

For approved decisions, reviewer, valid review date, verified sense and both exact text hashes are mandatory. Optional `reviewedReading` must be a nonempty, human-verified sentence reading; null means absent. Do not copy index sense numbers into `verifiedSense`. The ああ candidate currently teaches “that way,” rather than our interjection gloss, and must not be approved for that word meaning. Review fields on rejected decisions should still explain the reason, although the builder never publishes them.

Changing either source text invalidates its approval and fails the build until a new human review updates the hashes. Do not edit source Japanese/English text to fix an example without updating its review. Unknown approved candidate IDs, duplicate ledger decisions, invalid status, absent source IDs/URLs/license/owner fields and unsupported ledger versions fail the build. An explicit null owner is valid; never invent an author. Source URLs must match their IDs. With multiple valid approved candidates for one word, the lowest numeric Japanese ID, then English ID, wins; output is sorted by exact headword, reading and level. Input/ledger order does not affect the result.

## Output contract

`approved-examples.json` is a versioned object:

- `formatVersion`: 1.
- `sourceSnapshot`: the download date, three source file URL/byte/hash records and vocabulary SHA-256 from `coverage.json`.
- `examples`: one approved example per exact word key. Each includes `word`, `japanese`, `english`, `sentenceReading` (nullable), `japaneseId`, `englishId`, `japaneseSource`, `englishSource`, `japaneseOwner`, `englishOwner` (nullable), `license`, and `review`.
- `review`: reviewer, review date, verified-sense note, both source text hashes and `changes`. Text remains verbatim; adding a verified reading records `"Verified reading added"`.

Keep source IDs, links, license, owners, review metadata and snapshot hashes in released credits. Credit Tatoeba contributors, retain explicit missing-owner information, link [CC BY 2.0 FR](https://creativecommons.org/licenses/by/2.0/fr/) and explain modifications/readings. No audio is included. Future app packaging must include offline credits alongside the approved resource; this preparation output does not replace that requirement.

## Reviewer worksheet

`n5-review-sheet.csv` contains all 863 pending candidates, exact catalog glosses (including homograph senses), sentence IDs/text/hashes, and blank reviewer/date/sense/reading/notes fields. Regenerate with `python3 tools/data/export_review_sheet.py`. This is an export for human review, not an approval importer. A maintainer must transcribe completed human decisions into `approvals.json` with the exact nested word key and matching hashes; blank worksheet readings become null. Running the export resets the worksheet to pending, so keep completed review work separately. No worksheet decision is automatically trusted or published.

## Current catalog review preparation

`current-reconciliation.json` and `current-n5-review-sheet.csv` bind the retained corpus snapshot to `vocabulary-v2.json`. Generate them with:

```sh
python3 tools/data/prepare_current_examples.py
```

The script preserves `n5-candidates.json`, the original worksheet, raw snapshots, approval ledger and app resources. Legacy CSV rows are ordered stably by N5–N1, exactly as the catalog builder orders its `legacyMap` slots. Only that explicit mapping can select a current identity; absent, retired, ambiguous or missing targets remain unresolved with a cause. No headword-only fallback selects another sense. The full report retains every candidate, including candidates omitted from the worksheet.

The current worksheet selects one candidate per eligible N5 identity, in current catalog order, using the lowest numeric Japanese then English sentence ID, up to 30 identities. It includes current selected meanings, full sense notes, original legacy key, source texts/IDs/URLs/owners/license and exact text hashes. All rows remain pending; reviewer, date, decision, reason, verified-sense and reading fields are blank. The known ああ example is still pending and still requires rejection if it does not express the selected interjection sense. Binding an identity is not a sense approval.

Ledger version 2 retains the version 1 decision fields and adds mandatory `catalogID` and `contextSha256`. The context hash is SHA-256 over UTF-8 JSON containing precisely `id`, `headword`, `reading`, `level`, and `studyMeanings`, encoded with sorted keys, no ASCII escaping, and separators `(',', ':')`. Preserve the selected meaning order. Approved decisions must match the catalog identity, context hash, original candidate word key, both sentence IDs and both exact source text hashes. The builder revalidates the candidate context and refuses unresolved mappings, missing reviewer/date/sense rationale, source credit failures and altered source texts. Version 2 output preserves `catalogID`, `contextSha256` and `selectedStudyMeanings` alongside all prior attribution and reading provenance.

For a version 2 ledger the builder reads `current-reconciliation.json`; regenerate this report from the current catalog before building approved output. The CLI also checks approved contexts against the live catalog, rejecting a stale report after selected meanings change. Context changes require a fresh human decision and cannot silently carry over a legacy approval. Version 1 empty ledgers and synthetic legacy fixtures remain supported; a version 1 approval cannot publish a reconciled current-catalog record. Production `approvals.json` remains an empty version 1 ledger, so production has zero approved examples. Worksheet export does not import decisions or publish app content.
